## Response Section

### ความแตกต่างหลัก

* **รูปแบบข้อมูล:** JSON เป็นข้อความ (text) ส่วน Protobuf เป็นไบนารี (binary)
* **Schema:** JSON ไม่บังคับ (ใช้ JSON Schema เสริมได้) ส่วน Protobuf บังคับ ต้องนิยามในไฟล์ `.proto`
* **การอ่านด้วยคน:** JSON อ่านและแก้ได้ตรงๆ ส่วน Protobuf อ่านไม่ได้ ต้องถอดรหัสด้วยเครื่องมือ
* **ขนาดและความเร็ว:** JSON ใหญ่กว่าและพาร์สช้ากว่า (มีชื่อ key ซ้ำทุกชุดข้อมูล) ส่วน Protobuf เล็กกว่าและพาร์สเร็วกว่า
* **ชนิดข้อมูล:** JSON หลวม (ตัวเลขไม่แยก int/float ชัดเจน ไม่มีชนิดวันที่/ไบนารีในตัว) ส่วน Protobuf เข้ม (int32, int64, bool, bytes ฯลฯ)

### JSON

**ข้อดี**
- อ่านและ debug ง่าย ดูด้วยตาหรือเครื่องมือทั่วไปได้
- รองรับเกือบทุกภาษาและเบราว์เซอร์โดยตรง ใช้เป็นมาตรฐานของ REST API
- ไม่ต้องมีขั้นตอนสร้างโค้ดหรือแชร์ schema ก่อนใช้งาน

**ข้อเสีย**
- ขนาดข้อมูลใหญ่และพาร์สช้ากว่า โดยเฉพาะข้อมูลปริมาณมาก
- ไม่มี schema บังคับในตัว ข้อมูลผิดรูปแบบอาจหลุดเข้าระบบได้ถ้าไม่ตรวจเอง
- ชนิดข้อมูลหลวม อาจเกิดปัญหา เช่น ตัวเลขใหญ่คลาดเคลื่อนใน JavaScript
### Protocol Buffers

**ข้อดี**
- ขนาดเล็กและเร็วกว่า ประหยัด bandwidth และ CPU เหมาะกับ service ที่เรียกกันถี่
- มี schema ชัดเจนและ type ที่เข้ม ทำให้สัญญาระหว่าง service ตรงกัน
- สร้างโค้ดอัตโนมัติจาก `.proto` ได้หลายภาษา และรองรับการเปลี่ยน schema อย่างปลอดภัยผ่านเลขฟิลด์ (backward/forward compatible)
- ใช้คู่กับ gRPC ได้โดยตรง

**ข้อเสีย**
- อ่านด้วยตาไม่ได้ debug ยากกว่า ต้องมีเครื่องมือถอดรหัส
- ต้องจัดการไฟล์ `.proto` และขั้นตอนสร้างโค้ด ทำให้ซับซ้อนกว่า
- เบราว์เซอร์ใช้ตรงๆ ไม่สะดวก ต้องอาศัยตัวช่วย เช่น gRPC-web
- ต้องระวังเรื่องเลขฟิลด์ ห้ามนำเลขที่เคยใช้แล้วกลับมาใช้ใหม่
- ใน proto3 แยกไม่ได้ว่า "ไม่ได้ส่งค่ามา" กับ "ส่งค่า 0 / ข้อความว่าง / false" เพราะค่าเริ่มต้นไม่ถูกส่ง ต้องใส่ `optional` ถ้าต้องการแยกสองกรณีนี้

### การเลือกใช้

JSON เหมาะกับ API ที่เปิดให้ภายนอกหรือฝั่งเว็บเรียกใช้ และงานที่ต้องการความง่ายในการ debug ส่วน Protobuf เหมาะกับการสื่อสารระหว่าง service ภายในที่ต้องการความเร็ว ขนาดเล็ก และสัญญาข้อมูลที่ชัดเจน
